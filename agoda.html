2. 🚀 เคสประสบการณ์และบทพูดแบบ STAR Technique (STAR Experience Stories & Frameworks)

2.1 การทำ Solution Design & High-Level Sizing เพื่อการ Prioritize + ตัวอย่างการคำนวณ RICE Framework

Key Concept: ถือเป็น "สะพานเชื่อมชิ้นสำคัญที่สุด" (The Ultimate Bridge) ระหว่างสายงาน Engineering กับ Product Management เพราะ PM ต้องนำ Cost/Effort Score จาก RICE Framework ไปหารกับ Business Value เพื่อคำนวณหา ROI ในการตัดสินใจว่าฟีเจอร์นี้คุ้มค่าที่จะทำในสปรินต์นี้หรือไม่

Key Pitching Points:

  • Data-Backed & Risk-Adjusted Sizing: ประเมินจาก Technical Complexity, Dependencies, Data Migration Risks, และ Testing Effort โดยไม่มโนตัวเลข
  • Good-Better-Best Options (Trade-off Matrix): นำเสนอทางเลือกให้ PM เห็น Trade-off ชัดเจน เช่น Option A (Quick Win / MVP): ใช้เวลา 1 สัปดาห์ ปลดล็อก 80% ของ Value มี Tech Debt สั้นๆ vs Option B (Full Scalable Architecture): ใช้เวลา 4 สัปดาห์ รองรับ Multi-region & High Throughput
  • ช่วย PM คำนวณ ROI และ RICE Score: ส่ง Sizing ที่ชัดเจนและแบ่งเป็น Phase ช่วยให้ PM วาง Roadmap เลือกทำสิ่งที่มี High Impact / Low Effort ก่อนเสมอ

📊 ตัวอย่างคำนวณ RICE Score ในการประชุม Prioritization (RICE Worked Example):

สูตรการคำนวณ: RICE Score = (Reach × Impact × Confidence) / Effort

  • Reach (จำนวนผู้ใช้/ทราฟฟิก): วัดจากจำนวนคนหรือธุรกรรมที่จะได้รับผลกระทบในระยะเวลาที่กำหนด (เช่น ต่อเดือน)
  • Impact (ผลกระทบต่อเป้าหมาย): ให้คะแนนเป็นระดับ: 3 = Massive, 2 = High, 1 = Medium, 0.5 = Low, 0.25 = Minimal
  • Confidence (ความมั่นใจ): % ความมั่นใจในสมมติฐานและการประมาณการ: 100% = High Data Support, 80% = Medium Data, 50% = Low Data/Intuition
  • Effort (ทรัพยากร/เวลา): คิดเป็น Person-Months หรือ Story Points ของทีม Dev/QA

ตัวอย่างการเปรียบเทียบในสปรินต์:

  • Feature A (Free Cancellation Badge บนหน้า Search):
    Reach = 500,000 users/mo | Impact = 2 (High) | Confidence = 80% (0.8) | Effort = 0.5 Person-Month (1 สัปดาห์)
    RICE Score A = (500,000 × 2 × 0.8) / 0.5 = 1,600,000 🏆 (เลือกทำก่อน - ROI สูงมาก)
  • Feature B (Complex ML Personalization Engine):
    Reach = 100,000 users/mo | Impact = 3 (Massive) | Confidence = 50% (0.5 - ยังไม่มี data พิสูจน์) | Effort = 2 Person-Months (8 สัปดาห์)
    RICE Score B = (100,000 × 3 × 0.5) / 2 = 75,000 (ชะลอไว้ทำ Phase 2)

STAR Story:

  • S (Situation): ช่วงทำโปรเจกต์ระบบ Personalization Recommender ฝั่ง PM อยากได้ระบบวิเคราะห์พฤติกรรมผู้ใช้แบบ Real-time เพื่อเพิ่ม Conversion Rate แต่ทีมมีทรัพยากรจำกัด และเวลาเหลือเพียง 1 เดือนก่อน Peak Season
  • T (Task): บทบาทในฐานะ Lead SWE คือต้องทำ Solution Design และ High-Level Sizing เพื่อประเมินความเป็นไปได้เชิงเทคนิค และเสนอทางเลือกให้ PM นำไปตัดสินใจ Trade-off ระหว่าง Speed to Market vs System Complexity
  • A (Action): ออกแบบ Solution ออกเป็น 2 ทางเลือกพร้อม Sizing ที่ชัดเจนส่งให้ PM:
    1. Option 1 (Heuristic-Based / Low Effort): ใช้ Rule-based Logic ดึงข้อมูล Cache จาก Batch Processing ที่มีอยู่แล้ว (Sizing: 1 Developer / 4 วัน)
    2. Option 2 (Real-time ML Model / High Effort): สร้าง Event Stream via Kafka + Real-time Scoring Service (Sizing: 3 Developers / 3 สัปดาห์)
    กาง Trade-off Matrix ให้เห็นว่า Option 1 สามารถส่งมอบได้ในสปรินต์ถัดไป ให้ผลลัพธ์ Accuracy ราว 75% ของ Option 2 แต่ใช้ Effort เพียง 20% ทำให้ PM นำไปใส่ใน RICE Framework แล้วพบว่า Option 1 ให้ ROI สูงกว่ามากในแง่ Speed to Market
  • R (Result): PM ตัดสินใจเลือก Option 1 เป็น Phase 1 เพื่อปล่อยออกไปทำ A/B Testing ภายใน 1 สัปดาห์ ผลปรากฏว่า Conversion Rate เพิ่มขึ้น 12% ทันที และข้อมูลจากการทำ Experiment ช่วยให้ออกแบบ Solution Phase 2 ได้ตรงจุดมากขึ้น โดยไม่เสียเวลาทำ Over-engineering ตั้งแต่แรก

2.2 การบริหาร Trade-off ระหว่าง Bug Fix vs New Feature + ที่มาของ P0 / P1 / P2

💡 ที่มาและความหมายของ P0 / P1 / P2 (Priority Levels / Severity Matrix):

ตัวอักษร "P" ย่อมาจาก Priority / Priority Level ในระบบการบริหารจัดการ Software Incidents และ Issue Triaging สากล โดยเรียงลำดับตามความรุนแรงและผลกระทบต่อธุรกิจ:

  • P0 Priority Zero (Critical / Blocker / Stop the Line): ปัญหาขั้นวิกฤตที่สุดที่ทำให้กระทบ Core Customer Journey หลัก เช่น Payment Gateway ล่ม, Checkout System Crash, หรือเกิด Data Leak ➡️ SLA / Action: ต้องเข้าแก้ทันที (Immediate Hotfix) 24/7 หยุดงานอื่นทั้งหมด
  • P1 Priority One (High Severity): ฟังก์ชันสำคัญทำงานผิดพลาด แต่ระบบหลักยังไม่ล่ม หรือมีวิธีบรรเทาชั่วคราว (Workaround) เช่น คูปองส่วนลดไม่แสดงผลเฉพาะบางโรงแรม ➡️ Action: ต้องแก้ไขภายในสปรินต์ปัจจุบัน หรือจัดใส่ Hotfix ถัดไป
  • P2 Priority Two (Medium/Low Severity / Cosmetic): ข้อผิดพลาดเล็กน้อย เช่น UI Alignment เบี้ยว, ข้อความสะกดผิด, หรือกระทบผู้ใช้งานกลุ่มน้อยมาก (< 1%) ➡️ Action: นำเข้า Backlog เพื่อประเมิน RICE Score แข่งกับ New Features ในสปรินต์ถัดไป

Sprint Capacity Allocation (โควต้าใน Sprint):

  • 70% Feature Development: เพื่อขับเคลื่อน Business Goals / OKRs
  • 20% Bug Fixes & Technical Debt: เพื่อรักษาคุณภาพของ Product / Team & System Health
  • 10% Buffer / Unplanned Tasks: สำหรับ P0 Hotfixes หรือ Production Monitoring

STAR Story:

  • S (Situation): ช่วงรันสปรินต์ก่อนเปิดตัวแคมเปญใหญ่ ทีมย่อยของเรามีคิวต้องส่งมอบ New Checkout Feature เพื่อเพิ่ม Conversion Rate แต่ในขณะเดียวกัน เรามีคิว Bugs ค้างอยู่ใน Backlog กว่า 15 รายการ รวมถึง Bug ด้าน UI Glitch บนมือถือบางรุ่นที่มี Traffic ประมาณ 3%
  • T (Task): ฝั่ง Business ต้องการให้ดัน Feature ใหม่ให้เสร็จ 100% แต่ฝั่ง Dev และ QA กังวลเรื่องการสะสม Technical Debt และอยากเคลียร์ Bugs ทั้งหมดก่อน บทบาทคือต้องหา Trade-off ที่เหมาะสมที่สุดโดยไม่กระทบเป้าหมายธุรกิจและไม่ทำให้คุณภาพระบบพัง
  • A (Action):
    1. Bug Severity & Impact Triaging: จับมือกับ QA และ Dev เพื่อทำ Bug Classification โดยดูจาก Affected Users (%) และ Revenue Impact พบว่าจาก 15 Bugs มีเพียง 2 รายการที่เป็น P1 Bug ที่มีผลต่อ Drop-off Rate จริงๆ ส่วนอีก 13 รายการเป็น P2 Minor Cosmetic Glitches
    2. RICE Score Comparison: นำ Feature ใหม่ และ Bugs 2 รายการสำคัญนั้นมาเข้าตารางประเมิน ROI ร่วมกัน เพื่อให้ทุกคนเห็นตัวเลขตรงกันว่า Feature ใหม่สร้าง Reach/Impact ต่อภาพรวมสูงกว่าอย่างเห็นได้ชัด
    3. Negotiated Capacity Allocation: เสนอทางเลือกให้ทีมว่า สปรินต์นี้เราจะ Fix เฉพาะ 2 High-Impact Bugs (ใช้ Effort 10%) เพื่อรักษา Quality ของ Core Flow แล้วทุ่ม Effort 80% ไปที่ New Feature ส่วน 13 Bugs ที่เหลือถูกจัดหมวดหมู่เข้า 'Bug Bash Day' หรือจัดสรรไว้ 15% ในสปรินต์ถัดไป
  • R (Result): ทีมสามารถส่งมอบ New Checkout Feature ได้ทันวันเปิดแคมเปญ ดัน Conversion Rate ขึ้นมาได้ 8% ในขณะที่ Core Flow ปราศจาก Critical Bugs ช่วยลดตั๋ว Support จากลูกค้าลงได้ 15% และทีม Dev รู้สึกว่าคำตัดสินใจนั้นมีตรรกะรองรับ

2.3 การจัด Sync-up Meeting และบริหาร External Team

Key Value Points:

  • Alignment & SLA Definition: กำหนด Objective, Single Point of Contact (SPOC), Cadence (ความถี่ประชุม) และ Communication Channel (Dedicated Slack/Teams Channel + Weekly Sync)
  • Technical API & Dependency Mapping: ตกลง API Contracts, Data Schema Alignment, Environment Sandbox/Staging, และ Error Handling Specifications ร่วมกับทีมภายนอกตั้งแต่วันแรก
  • Risk Management & Blocker Clearing: ระบุและติดตาม Blockers/Dependencies อย่างใกล้ชิด หากฝั่ง External ทำงานล่าช้ากว่าแผน มีการทำ Escalation Path หรือเตรียม Fallback/Mock Solution เพื่อไม่ให้กระทบ Internal Timeline

Meeting Structure (Pre / During / Post):

  • Pre-meeting: ส่ง Agenda & Target Outcomes ล่วงหน้าอย่างน้อย 24 ชม. พร้อมระบุว่าต้องการการตัดสินใจเรื่องอะไรในรอบนี้
  • During Meeting: ใช้ Action-Oriented Tracking (โฟกัสเฉพาะ Blockers, Technical Mismatches, และ Upcoming Dependencies) + Timeboxing & Parking Lot หากถกเทคนิค deep เกินไป
  • Post-meeting: สรุป MoM (Minutes of Meeting) / Action Items ที่ชัดเจนเสมอ (Who does What by When) แล้วส่งกลับไปให้ External Team เซ็นรับทราบ/ยืนยันในแชทหรืออีเมลเพื่อป้องกันปัญหา

STAR Story:

  • S (Situation): ช่วงทำโปรเจกต์ Integration ระบบ Payment Gateway ใหม่กับทีม Vendor ต่างประเทศ เพื่อรองรับวิธีการชำระเงินท้องถิ่นแบบใหม่ในภูมิภาค มีเวลาเพียง 8 สัปดาห์ในการทำ Integration & E2E Testing แต่ทีม External มีกระบวนการทำงานที่ค่อนข้างช้า ตอบอีเมลล่าช้า และยังไม่มี API Documentation ที่สมบูรณ์
  • T (Task): บริหารจัดการและ Sync งานกับ External Team ให้ทันตามแผนโดยไม่กระทบวัน Launch
  • A (Action):
    1. Establish Single Communication Hub: เปิด Slack Connect Channel ร่วมกัน และเปลี่ยนการคุยผ่านอีเมลสัปดาห์ละครั้ง มาเป็น Bi-weekly 30-min Sync-up Meeting ที่เน้นคุยเรื่อง Blockers เท่านั้น
    2. Technical Alignment & Contract First: ใช้ความรู้ฝั่ง Dev ดึงทีม Tech ทั้งสองฝั่งมาตกลง API Specification & Data Mapping ตั้งแต่วันแรกผ่าน Postman Collection
    3. Proactive Dependency Tracking & Mocking: สร้าง Joint Dependency Board (Jira/Trello) และสั่งให้ทีมภายในสร้าง Mock API Server ขึ้นมาก่อน เพื่อให้ทีมเราทำ Frontend & Business Logic ล่วงหน้าได้โดยไม่ต้องนั่งรอ
  • R (Result): ทีมทำ Integration Test ได้ทันทีที่ External API Sandbox พร้อม ลดเวลาการทำ E2E Testing ลงได้ 2 สัปดาห์ โปรเจกต์เปิดใช้งานได้ตรงตามเป้าหมาย 100% โดยไม่มี Downtime

2.4 การบริหารเวลาส่วนบุคคลด้วย Outlook Timeboxing

Key Value Proposition:

  • เปลี่ยนจาก To-Do List เป็น Timeboxed Calendar: To-Do List ขยายตัวเรื่อยๆ ไม่มีเวลาแน่นอน แต่การบล็อกเวลาบน Outlook คือการทำสัญญา Fixed Capacity กับตัวเอง บังคับให้ทำ Prioritization ตามเวลาที่มีจริง
  • ปกป้องเวลาสำหรับ Deep Work (Focus Time): ลงสล็อตเวลาล่วงหน้า (วันละ 1.5–2 ชั่วโมง) ป้องกันไม่ให้คนอื่นกดนัดประชุมแทรกเข้ามาช่วงต้องใช้สมาธิวิเคราะห์งาน
  • Task Batching / Color-Coding:
    • 🔴 Red / Orange: Critical Meetings & Alignment (Sync-up, Stakeholders)
    • 🔵 Blue: Deep Work / Product Strategy (PRD, Backlog Refinement, Data Analysis)
    • 🟢 Green: Team Coaching / 1-on-1s / Retrospectives
    • 🟡 Yellow: Admin, Email, Jira Maintenance, Slack Catch-up (Shallow Work)

STAR Story:

  • S (Situation): ช่วงต้องควบทั้งบทบาท Lead/PO และคุมโปรเจกต์ใหญ่ วันๆ มีทั้งประชุมด่วน, แชตถามทางเทคนิคจากทีม Dev, งานเอกสาร Jira และการวาง Timeline ทำให้ช่วงแรกต้องทำงานล่วงเวลาบ่อยเพราะเวลากลางวันหมดไปกับ meetings
  • T (Task): คุมปฏิทินเพื่อเรียกคืนเวลา Deep Work กลับมาสร้าง High-Value Output
  • A (Action):

AND fire the analytics event: `checkout_promo_applied` with parameters `{code: "AGODA10", discount_value: 10}`. 3. 🔍 การวิเคราะห์ Gap Analysis, กลยุทธ์การปิด Gap 9 มิติ และคลังคำศัพท์เฉพาะ (Glossary)

มิติ Gap สิ่งที่จะโดนถาม/ลองเชิงในห้องสัมภาษณ์ แนวทาง / เทคนิคการตอบเพื่อปิด Gap
1. Data Analytics & Experimentation North Star, Primary/Guardrail Metrics, p-value, Sample Size, SRM เน้นว่าคุ้นเคยกับ Data แม้เดิมเน้น System Data แต่ศึกษากรอบ A/B Testing & Funnel มาอย่างดี
2. Strategic Thinking & Market Acumen 0-to-1 Ambiguity, Unit Economics, CAC vs LTV, Take Rate, P&L ถอยกลับมาเริ่มที่ User Problem + Business Impact เสมอ ห้ามกระโดดไปคิด Architecture ทันที
3. Customer Empathy & User Research Unmet Needs ก่อนมี Data, User Interview, Usability Testing โชว์การนำ User Feedback มาผสมกับ Data Analytics เพื่อตั้งสมมติฐานก่อนทำ PRD/Sizing
4. Executive Alignment ขายไอเดียกับ Executives, การปฏิเสธเมื่อ Data บอกไม่คุ้มทำ ดึงทักษะ Data-backed Communication ใช้ Data และ Business ROI เป็นตัวเชื่อมโยง
5. Monetization & Unit Economics Bottom-line Trade-off (Conversion vs Support Cost) เชื่อมโยงผ่าน Top-line Growth (Conversion) และ Bottom-line Savings (Cloud Cost)
6. Post-Launch Evaluation มอนิเตอร์ผลหลัง Release 2-4 สัปดาห์, ผล A/B Inconclusive อธิบายขั้นตอน Post-Launch Observability Phase ผ่าน DataDog & CloudWatch Monitoring
7. Failing Fast & Product Deprecation การใช้ Data พิสูจน์แล้วเด็ดขาดในการถอด/ฆ่าฟีเจอร์ที่ไม่สร้าง Value ใช้เคส Decommission Legacy Servers/Services ที่ไม่มี Traffic เพื่อลด Tech Debt & Cloud Cost
8. High Ambiguity (0 to 1) โจทย์กว้างมาก เช่น 'ถ้า Agoda จะเปิดจองตั๋วรถไฟใน SEA' ใช้ Problem Decomposition Framework และ Hypothesis-Driven Approach แตกโจทย์
9. Global Scale & Localization บาลานซ์ระหว่าง Global Scalability กับ Local Relevance ชู Modular Design: Core Engine เดียวกันหลังบ้าน แต่เปิด Flex Layer ปรับเปลี่ยนหน้าบ้าน

📖 คลังคำศัพท์เฉพาะในหัวข้อ Gap Analysis (Technical & Business Glossary):

  • North Star Metric: ตัววัดหลักตัวเดียวที่สะท้อนคุณค่าสูงสุดที่ลูกค้าได้รับและขับเคลื่อนการเติบโตระยะยาวของบริษัท (เช่น Search-to-Book Successful Transactions)
  • Primary Metric vs Guardrail Metric: Primary Metric คือตัวเลขเป้าหมายหลักที่อยากดันขึ้น (เช่น Conversion Rate +2%) ส่วน Guardrail Metric คือตัวเลขการทำงานของระบบหรือธุรกิจที่ห้ามพังเด็ดขาดขณะรัน Experiment (เช่น Page Latency p95 ห้ามช้าลง, Cancellation Rate ห้ามพุ่ง)
  • p-value (Statistical Significance): ค่าความน่าจะเป็นทางสถิติเพื่อพิสูจน์ว่าผลลัพธ์ที่ B ชนะ A ไม่ได้เกิดจากความบังเอิญ โดยปกติที่ Agoda ต้องมีค่า p-value < 0.05 (ระดับความเชื่อมั่น 95%)
  • SRM (Sample Ratio Mismatch): ข้อผิดพลาดทางสถิติเมื่ออัตราส่วนผู้ใช้ที่สุ่มเข้า Control vs Treatment ไม่ตรงตามสเปกที่ตั้งไว้ (เช่น ตั้งไว้ 50/50 แต่ผลจริงออกมา 60/40) สัญญาณบอกว่าระบบสุ่มทราฟฟิกมีบัก
  • MDE (Minimum Detectable Effect): ขนาดการเปลี่ยนแปลงเล็กที่สุดของ Metric ที่การทดลอง A/B Testing จะสามารถตรวจจับได้ทางสถิติอย่างแม่นยำ
  • 0-to-1 Ambiguity vs 1-to-N Optimization: 0-to-1 คือการสร้างสิ่งใหม่จากศูนย์ท่ามกลางความกว้างและความไม่แน่นอนสูง ส่วน 1-to-N คือการปรับปรุงหรือต่อยอดฟีเจอร์เดิมที่มีข้อมูลอยู่แล้ว
  • Unit Economics: การวิเคราะห์รายรับและต้นทุนตรงต่อหน่วยการขาย 1 Transaction (เช่น Gross Profit ต่อ 1 Booking หลังหัก Payment Fee และ Marketing Cost)
  • CAC (Customer Acquisition Cost) & LTV (Lifetime Value): CAC คือต้นทุนการได้มาซึ่งลูกค้าใหม่ 1 คน ส่วน LTV คือมูลค่ารวมตลอดช่วงชีวิตที่ลูกค้าคนนั้นจะสร้างรายได้ให้บริษัท (สูตรสุขภาพดี: LTV > 3 × CAC)
  • Take Rate / Commission Margin: สัดส่วน % คอมมิชชั่นที่ Agoda เรียกเก็บจากโรงแรม/คู่ค้าต่อ 1 ยอดจอง (เช่น 15-20%)
  • DataDog / CloudWatch APM (Application Performance Monitoring): เครื่องมือมอนิเตอร์สุขภาพระบบแบบ Real-time ดักจับ Latency p95/p99 และ HTTP Error Status Codes (4xx/5xx)

💬 สคริปต์การนำประสบการณ์เทียบเคียงมาปิด Gap เชิงลึก (Framing Scripts)

1. ด้าน Monetization / P&L (Top-line & Bottom-line):
"ในบทบาทเดิมผมอาจไม่ได้คุม P&L โดยตรง แต่ผมเข้าใจ Business Lever ผ่าน 2 ฝั่งเสมอ: 1) Top-line Lever: Optimizing Conversion Funnel และลด Latency หน้า Checkout เพื่อป้องกัน Drop-off Rate, 2) Bottom-line Efficiency: คุม COGS และ Server Infrastructure Cost เพื่อให้ Unit Economics ดีขึ้นครับ"

2. ด้าน Post-Launch Evaluation (DataDog & CloudWatch Monitoring):
"หลัง Release ผมไม่ได้จบแค่ Demo แต่มีขั้นตอน Post-Launch Observability Period (2-4 สัปดาห์) ผ่าน DataDog/CloudWatch มอนิเตอร์ 3 กลุ่ม: Operational Health (Error 4xx/5xx, APM), Performance Guardrails (Latency p95/p99), และ User Adoption Signals (Transaction Success Rate) หาก Latency/Error พุ่ง มี Rollback Plan ทันทีครับ"

3. ด้าน Product Deprecation / Sunset (Decommissioning Legacy Servers):
"ตัวอย่างการทำ Sunset ของผมคือ Decommission Legacy Servers/Services ที่ไม่ได้สร้าง Value โดยวิเคราะห์ Traffic Pattern บน CloudWatch/DataDog พิสูจน์ว่าไม่มี Active Users วางแผนปิด Step-by-Step ร่วมกับ Dev ช่วยลดค่าใช้จ่าย Cloud Infrastructure ลงได้ X% นำ Budget ไปลงทุนฟีเจอร์ใหม่ที่คุ้มค่ากว่าครับ"

8.3 เจาะลึก A/B Testing Mechanics & Pivot Strategies

A/B Testing Definition: ระเบียบวิธีทางวิทยาศาสตร์ที่เปรียบเทียบระหว่าง Control (Variant A - เวอร์ชั่นเดิม/Baseline) กับ Treatment (Variant B - เวอร์ชั่นใหม่ที่ปรับเปลี่ยน) สุ่มผู้ใช้ 50/50 เพื่อวัดนัยสำคัญทางสถิติ (p-value < 0.05)

Agoda 5-Step Experimentation Framework:

  1. Formulate Hypothesis: "If we highlight 'Free Cancellation' badge in green on SRP, Conversion Rate will increase by 0.5%."
  2. Design Metrics: Define Primary Metric (Conversion Rate), Secondary (CTR), Guardrail (Page Load Latency & Cancellation Rate)
  3. Implementation & Feature Flagging: Eng builds feature behind Feature Flag Platform with Event Tracking Tagging Schema
  4. Run & Monitor: Randomize users 50/50, monitor for SRM or metric spikes in first 24-48 hours
  5. Decision Making: If Win (p < 0.05) ➡️ Ship 100%; If Loss/Inconclusive ➡️ Rollback 0% & Analyze RCA

A/B Testing Pivot Script (กรณีไม่เคยทำ A/B Test บน Production ใหญ่มาก่อน):
